# Remote Play setup helper — source, scope, and API

This separate payload is a modified derivative of **PS5 Account Tools**, pinned to
[MangoScango/ps5-account-tools commit 8d648caef776d3b35af3faad36bc534b9127fe3c](https://github.com/MangoScango/ps5-account-tools/tree/8d648caef776d3b35af3faad36bc534b9127fe3c).
It is distributed under GPL version 3; the unmodified upstream license and exact
reference files are in `third-party/account-tools/`. `SOURCE.json` records SHA-256
for each vendored file. The app's AGPL license does not replace this separate
helper's license. Distribute these sources and notices with the helper binary.

`config.inc` retains upstream language/region lookup and config construction.
`setup.c` derives the registry-key/config-offset schema from `npsignin.c` and the
account-ID registry key from `offact.c`. `platform.c` derives checked process
credential setup from `sys_lite.c`. Upstream credits ps5-payload-dev/offact for
GPL registry plumbing, earthonion/np-fake-signin for fake sign-in, and
soniciso/elf-arsenal for its foundation. Original source headers are preserved.

**Asset provenance is incomplete.** `auth_dat.h` and `config_dat.h` are byte-for-byte
upstream NP-state templates, not templates generated by this project. The pinned
headers contain neither a separate asset license nor an explanation of how those
bytes were obtained; repository GPL text alone does not independently establish
rights in any underlying proprietary format/content. We verified source origin
and hashes, not ownership, originality, a valid Sony credential, or firmware
compatibility. Review that uncertainty before distributing or using this helper.

## Build and evidence

Run `python3 scripts/build-remoteplay-setup.py` after the existing SDK bootstrap.
It uses the checksum-pinned PS5 Payload SDK v0.43 / LLVM toolchain already used by
padd and emits `build/remoteplay-setup.elf` and its SHA-256/source report. No
libmicrohttpd is present in that SDK; the payload uses a small bounded HTTP server.
No browser, controller, app, reboot, or console connection is triggered by the
build. An unconfigured bundled ELF refuses startup before privilege initialization. The
app patches its single 64-byte deployment marker with a new random session secret.
A configured start initializes only the helper process's credentials and UserService,
checks each initialization result, and opens TCP port **6770**. It does not create
backups or modify account files/registry until an explicit POST.

`uv run pytest -q tests/test_remoteplay_setup_payload.py` runs recording-backend
transaction and HTTP socket-pair tests without a console. It covers selected slot
3 isolation, all 23 registry setter failure positions, file/backup failures,
checked rollback, failed recovery refusal, existing-ID preservation including
rollback, no-write retry, changed/ambiguous mapping, strict ID parsing, HTTP method
and origin checks, firmware refusal, and vendored hashes. Host transaction tests
run with UndefinedBehaviorSanitizer. AddressSanitizer's runtime deadlocks during
initialization on this machine's macOS 26.6.2 / Apple toolchain, so ASan results
are not claimed.

**Firmware 13.60 is a source-target gate, not a hardware validation claim.** The
SDK `kernel_get_fw_version()` reads the loaded libc's PS5 SDK version; v0.43's
`crt/kernel.c` identifies 13.60 as `0x13600000`. Inspection reports that version;
POST refuses other versions. Live service refresh, pairing, streaming, and whether
any particular account needs a user-coordinated reboot remain unvalidated.
Target-only writes for later slots deliberately avoid upstream's base-slot mirror;
whether additional firmware behavior is necessary for those slots is unknown.
Only a unique, exact, untruncated mapping to the selected **foreground logged-in
user** is accepted. The helper does not claim UID-to-slot identity beyond those
UserService/registry name checks.

## HTTP contract, version 1

LAN only. Every port-6770 request requires `Authorization: Bearer <64-lowercase-hex>`.
The app generates 32 random bytes with SecRandomCopyBytes, replaces exactly one
fixed-length ELF marker in memory, and refuses missing/duplicate markers. The
helper validates that it was configured, compares bearer bytes without an early
exit on differing values, and refuses expired credentials. There is no compiled
usable default. A monotonic 15-minute lifetime bounds both request authorization
and an idle listener. One well-formed, authorized preparation attempt is allowed
per launch; an attempt is consumed immediately before the transaction, including
an attempt that fails or restores changes. GET inspection remains available until
expiry, and authenticated `POST /api/shutdown` can stop the serial listener.

Keep using a trusted LAN. This bearer mechanism does not provide transport
encryption, authenticate console identity, secure the separate unauthenticated
Payload Manager, or protect against someone who can read/replace the uploaded ELF
through existing privileged console services. The secret is embedded in that
uploaded console file and in the running helper. The Mac keeps it only in a
per-host memory map for this app run; wizard reopen reuses it, app restart loses
it. Never put it in URLs, preferences, logs, or diagnostic responses. If an old
helper cannot authenticate, stop that process on the console or wait for its
15-minute expiry; the app refuses to upload/launch over that conflict.

Starting a new helper first authenticates an existing listener, shuts down its
own old session, uploads a newly personalized ELF, and checks a versioned,
authenticated GET after launch (bounded read-only retries allow listener startup).
Loader HTTP success alone is not accepted as a successful helper start. The
transport refuses all redirects on both ports 6770 and 8084. Closing the wizard
suppresses its callbacks but allows an accepted preparation request to finish;
closing cannot undo console writes. Reopen and inspect before another attempt.

Responses contain account identifiers; do not log bodies. No CORS is enabled and
any `Origin` header is rejected. Native callers must require this exact helper ID,
version, and all six capabilities, including `session-auth`; unmodified Account
Tools on port 6769 and the earlier unauthenticated derivative are incompatible.

`GET /api/accounts` is read-only and returns:

```json
{"ok":true,"helper":"ps5mcp-remoteplay-setup","version":1,"firmware":"13.60","hardwareValidated":false,"capabilities":["compare-before-write","preserve-existing-id","target-slot-only","durable-backup","checked-readback","session-auth"],"accounts":[{"userId":268435457,"name":"Offline","slot":1,"accountId":"0x0000000000000000","accountIdB64":"AAAAAAAAAAA=","activated":false,"signedIn":false,"foreground":true,"preparationVerified":false}]}
```

`activated` means nonzero registry ID; `signedIn` means nonzero registry sign-in
flag. `preparationVerified` adds file contents/selected account and all manifest
registry-value consistency checks. None establishes live streaming readiness.
Enumeration failure or ambiguous mapping returns `ok:false` with
`code:inspection-failed`; account enumeration is all-or-nothing. Only up to four
logged-in users are enumerated; all sixteen registry names are checked for
ambiguity. Read failures are not treated as empty slots.

`POST /api/prepare` requires both headers:

```text
Content-Type: application/x-www-form-urlencoded
X-RemotePlay-Setup: 1
```

The bearer header above is mandatory for inspection, preparation, and shutdown.
The literal `X-RemotePlay-Setup: 1` header is only a request-shape/CSRF check and
does not authorize anything. Its body has exactly three fields, in any order:

```text
userId=268435457&slot=1&expectedAccountIdB64=AAAAAAAAAAA%3D
```

`userId` and `slot` are canonical decimal integers; account ID is canonical Base64
of exactly eight little-endian bytes, URL-encoded including `+`, `/`, and `=`.
The all-zero ID must be supplied explicitly. Missing/duplicate fields, invalid
padding, overflow, trailing values, and unsupported verbs/routes are refused.
No GET mutations, sign-out, deactivate, or arbitrary account-ID API exist.
`POST /api/shutdown` requires the bearer header, `X-RemotePlay-Setup: 1`, and a
zero-length body; it never interrupts the serial preparation transaction. The caller must show the selected account and exact persistent effects
below and obtain user confirmation before this POST. GET discovery and helper
startup do not authorize preparation.

Success returns HTTP 200, `ok:true`, `partialWrites:false`, `code:prepared`, a
nonempty `backupPath`, `account.preparationVerified:true`, and `noOp:false`.
A verified prepared account instead returns `code:already-prepared`, `noOp:true`,
no account writes, and an empty backup path. `requiresUserReboot:false` means no
automatic reboot request was issued; it is not proof a reboot is unnecessary.
`liveServiceStateVerified:false` explicitly distinguishes persisted readback from
running system-service state. Both new and existing nonzero account IDs are
represented as strings. Native callers should validate the returned account
matches the selected UID/slot and preserve a previously nonzero ID exactly.

Failures return HTTP 400/401/409/404 as applicable and `ok:false`. Inspect `code` and
JSON `ok`, not status alone. Transaction responses include `partialWrites`,
`restored`, and `backupPath`. `partialWrites:true,restored:true` means writes were
attempted and verified restoration completed; it is still a failed preparation.
`recovery-required` means automatic restoration was not fully verified or an
interrupted/prior transaction marker exists; never automatically retry mutation.

## Exact persistent effects and recovery

For the explicitly selected UID only:

- Create `/system_data/priv/home/<uid-hex>/np/` with mode 0755 if absent (preserving
  an existing directory's mode), then atomically replace
  `np/auth.dat` with the pinned auth template and `config.dat` with the pinned
  config template patched with that username, system language/region, generated
  offline email, and selected account ID.
- Preserve any nonzero account ID without calling its setter. For ID zero only,
  assign a nonzero random eight-byte value using the SDK's `arc4random_buf`.
- Write the selected slot's email, online ID, NP environment, country, language,
  locale, template flags/NP integers, extension fields, account ID when zero,
  and finally its sign-in flag. The exact 23-key/config-offset manifest is the
  `fields` table in `setup.c`; every key uses `(slot-1)*65536`. The narrow legacy
  exception below leaves its unavailable key untouched, and the bounded six-field
  policy preserves the explicit opaque NP fields without setters.
- Store original files/presence and all original registry values in
  `/data/remoteplay-setup/<uid-hex>.snapshot`, plus a durable transaction state
  marker `<uid-hex>.state`. Those backups may contain sensitive original NP
  state and use mode 0600 files in a mode 0700 backup directory. Keep them private. Successful prepared
  no-op retries create neither files nor registry changes.

Each backup is checked by readback before account changes. File operations check
complete reads/writes, fsync/close/rename/directory-sync errors, avoid final-path
symlinks, and reject nonregular/oversized files. Registry setters and their
readbacks are checked. Identity and all original values are compared after the
backup; identity is checked again during registry updates. An existing sign-in
flag with inconsistent/unknown NP state is refused for manual review.

On a normal failure the helper attempts restoration of every touched value/file
and verifies it, retaining the snapshot. It does not restore into an account whose
mapping or account ID has changed unexpectedly. A pending marker survives a
process crash; a later request refuses new mutations unless the entire persisted
state already verifies as prepared. No automatic reboot or startup repair occurs.
There is no post-crash restore endpoint: preserve the snapshot and seek reviewed
recovery using that exact matching build and target identity. The snapshot is a
versioned native C structure (`rp_snapshot` in `setup.c`), not a general-purpose
portable backup format. After successful verification a complete marker and
snapshot remain; externally changed state requires review before another change.

The console registry has no atomic multi-key compare-and-swap. These checks and
rollback cannot guarantee isolation against another process changing the same
account during the transaction, atomic behavior across power loss, restoration
of services' in-memory state, or preservation of filesystem ACLs/extended attributes
when replacing an existing file. Existing POSIX ownership and mode are preserved. Avoid simultaneous account-management activity.
The payload reports persisted byte consistency only; hardware acceptance is a
separate step requiring explicit device-mutation authorization.

## Read-only registry diagnostics

`python3 scripts/build-remoteplay-setup.py --diagnostics` builds the separate
`build/remoteplay-setup-diagnostics.elf`. This one-shot payload resolves only the
unique foreground logged-in user, probes all 23 manifest fields for that selected
slot, and writes `/data/remoteplay-setup.diagnostics.json` with mode 0600. It opens
no listener and has no HTTP preparation route, registry setters, account-file
writes, or startup account repair. It still initializes its own process
credentials and UserService to read the same protected registry as the helper.
The build audits its dynamic imports to reject registry mutators.

The report contains target UID/slot, numeric key/kind/requested size, signed and
hex return status, and a final target-stability check. It does not contain the
username, account ID, registry values, NP files, PINs, or session credentials.
String fields additionally probe larger 65/128/256-byte buffers. Failed fields
add alternate string/binary reads with 1/4/8/17/65/256-byte buffers, reporting only
statuses. These diagnostic observations never change the mutation manifest,
substitute defaults, or convert a failed backup into a successful one.

Preparation failures during registry backup now include the exact key, kind,
size, and signed/hex status in both the message and `registryError` JSON object;
no registry/file account writes have occurred at that stage. `kind` values are
0 = integer, 1 = string, 2 = binary. Other unset/missing/invalid keys are not assumed recoverable: preparation
remains blocked until their schema and backup semantics are established. Pinned upstream labels base key 125830144 as the
integer at config offset 0x48 but discards setter errors; that label alone does
not establish support on a particular PS5 firmware. SDK import stubs and the
[OpenOrbis RegMgr declaration](https://github.com/OpenOrbis/OpenOrbis-PS4-Toolchain/blob/master/include/orbis/RegMgr.h)
confirm the getter call signatures, not firmware key validity or error meaning.

Both helper build variants validate all vendored reference hashes against the
pinned `SOURCE.json` before compilation and record `upstream_sources` plus
`template_hashes` in their build report. Hash verification establishes exact
source origin only; it does not resolve the NP-template rights uncertainty above.


### Narrow 13.60 legacy-key exception

A coordinator-run read-only investigation on 2026-10-15, using the newly created
User1 foreground account in slot 2 on firmware 13.60, found that target key
125895680 (base 125830144 plus one slot stride) returns exactly `0x800d0203` from
GetInt; all twelve alternate GetStr/GetBin size probes returned the same status.
The other 22 manifest fields read successfully. All larger string-buffer probes
succeeded. These observations rule out the initial generic string-buffer-size
hypothesis for that run. They establish that this key cannot be backed up through
those tested getters, not a value of zero or a verified meaning for its status.
Pinned upstream labels this the integer from config offset 0x48 and ignores its
setter result; that source does not demonstrate that the key is supported on
13.60. Omitting a rejected legacy registry entry is an inference from this source
and hardware evidence, subject to actual pairing/stream testing.

Only within the SDK-reported 13.60 family (`raw & 0xffff0000 == 0x13600000`), and only for base key
125830144 plus a valid selected-slot stride, exact return status `0x800d0203` is
represented as an unsupported field. Snapshot format version 2 stores an explicit
`unsupported_status` entry for it. Its cleared storage bytes are not a fabricated
registry value. The helper never calls its setter, compares it to template bytes,
or restores it during rollback. It checks that the same unsupported status still
holds before writing other fields. Final persisted-state verification permits
only this exact key/status/profile combination. A separate final transaction check
requires that support status remain identical to its backup marker: a readable
key becoming unavailable or an unsupported key becoming readable causes failure
and attempted restoration, rather than being accepted by the generic inspector. Readable legacy keys retain the
ordinary checked backup, write, readback, and rollback path. Other status codes,
other keys, or other firmware profiles remain hard failures before changes.

Host tests cover the exact exception, explicit version-2 snapshot marker, no
legacy setters during success or rollback, prepared no-op retries, a legacy key
becoming readable during backup, a readable legacy key's ordinary checked writes,
and refusal of the same status on other keys or unsupported firmware profiles.
This does not establish Remote Play readiness or authorize changes to an existing
user account; console validation is restricted to the separately authorized test
user.


The raw firmware diagnostic subsequently observed `0x13600007` while the formatted
version was `13.60`; the earlier equality against `0x13600000` therefore correctly
remained disabled but selected the wrong profile policy. Profile selection now
uses the SDK v0.43 primary convention from `crt/kernel.c`:
`switch(kernel_get_fw_version() & 0xffff0000)` with case `0x13600000`. Both the
HTTP preparation gate and legacy exception require that same 13.60 profile;
13.50, 13.61, and adjacent major families remain rejected. The low 16 raw build
bits are retained in `firmwareRaw` diagnostic metadata. Build reports and
authenticated account inspection expose a deterministic `build_id`/`buildId`
fingerprint over helper sources, verified upstream inputs, and builder source,
so a loaded revision can be distinguished without disclosing credentials.

### Checked write failure evidence and verified rollback

Registry write failures distinguish `setter`, `readback-read`, and
`readback-compare` phases. `registryError` retains the selected key/kind/size,
signed and hex setter/readback status, whether each operation actually ran,
zero-based first differing byte index (`-1` when unavailable), and bounded
expected/actual string lengths (`-1` for nonstrings or unavailable reads).
Neither failed nor successful values are serialized. A failed setter does not
pretend a readback ran. Byte comparisons remain strict; these diagnostics do not
normalize strings or excuse padding differences. The backup-read phase remains
separate and occurs before account writes.

Once a durable backup has been read back, each transaction also attempts to save
a private, unique `/data/remoteplay-setup/<uid>.<pid>.<serial>.trace.json` file.
It contains build ID, final success/failure/restoration flags, failure metadata,
and checked registry-step metadata only. It omits username, account ID, registry
bytes, NP contents, and authentication credentials. Its mode is 0600. The HTTP
result exposes `tracePath` and `traceSaved`; the latter requires checked file
write and readback. A diagnostic trace failure is reported independently and
never changes a verified account restoration into account success or failure.
Original snapshots remain the recovery evidence; a trace is not a backup.

For `partialWrites:true, restored:true`, the Mac explicitly reports that writes
were rolled back and verified, while retaining preparation failure and requiring
fresh inspection and a separate confirmation for another attempt. Network loss,
unverified restoration, and `restored:false` retain the warning that partial
changes may remain. Neither response causes an automatic preparation retry.

### Independent read-only restoration check

`python3 scripts/build-remoteplay-setup.py --verify-restoration` builds
`build/remoteplay-setup-restore-check.elf`. This one-shot payload writes only
`/data/remoteplay-setup.restoration.json` (mode 0600). Like the other read-only
probe, its build rejects registry mutator imports; it has no listener or
preparation route. It independently reads the unique foreground user's existing
snapshot and checks exact native structure size, magic, version 2, UID, slot,
every field's key/kind/size, allowed unsupported markers, and bounded file sizes.
Wrong or mismatched backups produce `snapshot-invalid` without reporting values.

`restorationVerified:true` requires the original account ID, every supported
registry value, the exact unsupported legacy-key status, both original file
contents/presence, an absent transaction marker, and stable foreground identity
to match. The report contains per-field/file booleans and statuses plus raw
firmware/profile/build metadata. It excludes names, account IDs, registry bytes,
NP contents, and credentials. A differing field/file, missing expected file,
unexpected file, retained marker, changed ID, or unstable target produces
`restorationVerified:false`. The audit calls no account mutator or restoration
routine. As with all registry reads, the comparison is not an atomic snapshot
against simultaneous external account-management activity.

### Bounded 13.60 preservation of opaque NP state

On the authorized fresh User1 test account, all earlier checked writes passed,
then A4 (base key 125830912) reported successful setter/getter statuses without
retaining the template value. Reviewed read-only sentinel probes established a
complete, deterministic int32 getter. A separate guarded write/read/restore
experiment observed original `0xfffffbff`, template `0xfffff9ff`, and readback
`0xfffffbff` (XOR `0x200`), followed by verified full restoration. The next bounded
preparation attempt similarly failed strict B4 readback and restored all original
state. These observations do not establish valid masks, normalization rules,
field meanings, or dependencies on sign-in ordering.

The next bounded 13.60 experiment preserves the complete upstream group of six
opaque NP integers: A4/B4/D0/D4/DC/F4, with explicit base keys 125830912,
125831936, 125832704, 125882625, 125854723, and 125833216. The irregular D4/DC IDs
are listed directly; no contiguous range is guessed. All four original bytes of
each field come from the checked snapshot and populate the corresponding
config.dat offset. None receives a setter during preparation or rollback. This
preserves existing account state without claiming these fields are read-only or
that their original values suffice for Remote Play.

Exact prewrite, in-transaction, final, and reopen comparisons remain, with no
masked or skipped bits. The sign-in-last order is unchanged. Rollback verifies
every preserved integer against its full original value even when failure
occurred before its forward index. If any field drifted, restoration is not
claimed and recovery-required is reported; no compensating setter is issued.
The preservation profile is captured at transaction entry and remains binding
through rollback if a later profile lookup fails.

Host tests parameterize all six fields, including both irregular keys, for
full-byte config preservation, zero normal/rollback setters, prewrite/during/
final/late-failure drift, and strict reopen verification. This remains a bounded
test-account experiment; general offline setup, pairing, and streaming are
unverified. Root's reviewed scratch probes supplied the hardware evidence; the
abandoned in-payload sentinel callback was removed. Standard read-only diagnostic
reports continue to disclose statuses only.


The following bounded extension additionally preserves only EXT_0x114C (base
125874195, size 65). On the same authorized User1 experiment, both setter and
getter reported success while expected string length was 64 and readback length
was zero. Readable snapshot restoration was subsequently verified. All 65 backed-up
bytes, including the terminator and padding, now populate config.dat. No 114C
setter is issued during preparation or rollback; full-size exact comparisons
remain, including padding-only drift. EXT_0x1100 and EXT_0x1141 retain their existing
checked writes and were verified before this failure. No raw string is included
in diagnostics.

The getter-based restoration audits cannot rule out hidden effects of an earlier
successful setter that its getter does not expose. Consequently, any later
User1 pairing/streaming success may still be confounded by prior experiments.
Generalizing this recipe requires a clean reproduction on a previously untouched
fresh test user. The preserved fields remain opaque; no read-only, normalization,
or sufficiency claim is inferred from these observations.
